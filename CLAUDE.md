## Суть

Опенсорсный калькулятор зарплат для digital-специалистов. Считает рыночную медиану по реальным данным из вакансий, а не по теоретическим оценкам. Открытый код, открытая методология, бесплатно для пользователей.

**Автор:** Дина — UX-редактор, фрилансер, автор Telegram-канала «Текст готов».
**Цель:** дать диджитал-специалистам понимание их реальной рыночной стоимости.
**URL:** https://digital-salary.vercel.app
**Репозиторий:** https://github.com/maisondina/digital-salary

## Архитектура (целевая, после рефакторинга мая 2026)

### Стек

- **Frontend + backend:** Next.js (App Router) + TypeScript
- **БД:** PostgreSQL на Supabase (free tier)
- **Хостинг:** Vercel (фронт + serverless functions + cron)
- **Тесты:** Vitest
- **Линтер/форматтер:** ESLint + Prettier

### Поток данных (целевой)

```
[Источники] → [Коннекторы] → [Нормализатор] → [Хранилище] → [Калькулятор] → [Frontend]
   SuperJob       fetch+parse    единый формат      JSON или      медиана       UI
   Habr Career                                      Supabase
   Telegram (+LLM)
   Trudvsem
```

**Ключевой принцип:** пользователь НЕ ждёт внешних API. Сбор данных идёт в фоне по cron'у раз в сутки. Фронт читает только из своего хранилища. Это даёт скорость (50–100 мс на расчёт) и автономность от чужих сервисов.

### Поток данных (фактический, на 12 мая 2026 — до рефакторинга)

В коде есть ДВА параллельных потока, и они не связаны:
1. **`src/scripts/updateData.ts`** — собирает данные с SuperJob (до 2000 вакансий), нормализует, считает медианы и навыки, пишет в `src/data/<профессия>.json`. Запускается вручную через `npm run update-data`.
2. **`src/app/api/salary/route.ts`** — при каждом запросе пользователя ИДЁТ В SUPERJOB ЗАНОВО (~10 сек), делает 1000 вакансий, считает на лету. JSON-файлы из (1) не использует.

**Первая правка в этом релизе** — переключить (2) на чтение из (1). Это даёт мгновенное ускорение без всякой БД.

### Хранилище — JSON или Supabase?

Решаем по факту. JSON-файлов в `src/data/` хватает для текущего объёма (4 профессии, ~10 KB на файл). Supabase нужна, если: 1) появится много источников и объём вырастет, 2) понадобится история по датам, 3) понадобятся сложные фильтры. Откладываем решение до момента, когда подключим Habr Career и Telegram.

### Источники данных (MVP)

Приоритет от наиболее релевантного к наименее:

| Приоритет | Источник | Тип доступа | Релевантность нише | Юр. статус |
|---|---|---|---|---|
| 1 | **Habr Career** | Открытые страницы + публичный salary report | Высокая (редакторы и UX в IT) | Чистый |
| 2 | **Telegram-каналы** | Официальный MTProto API + LLM для извлечения структуры | Очень высокая (фрилансеры, агентства, удалёнка) | Чистый (публичные каналы) |
| 3 | **SuperJob API** | Официальный (secret_key, ID 4125) | Средняя (традиционные работодатели) | Чистый |
| 4 | **Trudvsem.ru** | Открытый госpub API | Низкая для этой ниши, высокая по объёму | Чистый |

**Telegram-коннектор:** использует MTProto через telethon/pyrogram-аналог в Node.js (gramjs). Берёт посты из заданного списка публичных каналов, прогоняет через LLM (Anthropic/OpenAI) с extract-промптом для извлечения должности/вилки/города/навыков. Стоит ~$1–5/мес на нашем объёме.

**Парсинг hh.ru** — НЕ в MVP. Архитектура предусматривает его как будущий коннектор, но в этом релизе не делаем из-за серого юридического статуса.

### Расчёт зарплаты

Полная методология сбора, фильтрации, дедупликации, расчёта медианы и оценки навыков — в отдельном файле `METHODOLOGY.md` в корне проекта. Читать его в начале любой задачи, связанной с данными или расчётами.

Краткая суть:
- Формула диапазона: `from + (to - from) * 0.35`
- Базовая метрика: медиана по выборке (никаких средних)
- Минимум для отображения: 30 вакансий
- Спам-фильтр: агентства, > 3 SD выбросы, MLM-маркеры, короткие описания
- Округление: всё до 100 ₽ на финальном шаге
- Дедупликация: UNIQUE внутри источника + fuzzy-match кросс-источниковый

### Дедупликация

- Внутри источника: `UNIQUE (source, source_id)` на уровне БД — дубли физически невозможны
- Между источниками: fuzzy-match по `(работодатель, должность, город, диапазон зарплат)` с допуском
- Кросс-источниковые «возможные дубли» помечаются флагом, а не удаляются — для отладки

## Принципы продукта

- **UX-формулировки важнее технических.** «Ваша рыночная стоимость в Москве», а не «Медиана + коэффициент навыков».
- **Локализация на русском.** «UX-редактура», а не «UX-writing».
- **Прозрачность.** Методология описана на отдельной странице, доступна каждому.
- **Никогда не показывать недостоверные данные.** Лучше «недостаточно данных», чем рандомная цифра на трёх вакансиях.

## Что важно НЕ забывать

- **Кэш Vercel** при деплое — после обновления API/коннекторов часто нужно вручную сбросить
- **Городские ID разные у разных источников.** Москва: SuperJob = 4, hh = 1, Trudvsem = свой код. Маппинг живёт в `src/lib/cities.ts` (после рефакторинга)
- **Cron-задачи Vercel** работают по UTC, а не по Москве — закладывать запас по времени
- **Тесты обязательны** для: расчёта медианы, формулы диапазона, дедупликации, спам-фильтра

/tests              — Vitest
