# Методология сбора и обработки данных

> Сердце проекта. Каждое решение в коде должно ссылаться сюда. Если расчёт даёт сомнительный результат — значит либо данные плохие, либо логика не соответствует тому, что описано здесь.

## Принципы

1. **Точность важнее охвата.** Лучше показать «недостаточно данных» по узкому срезу, чем выдать медиану на 5 вакансиях.
2. **Свежие данные важнее объёма.** Сбор раз в сутки в фоне, никаких полугодовых снапшотов.
3. **Прозрачность.** Пользователь видит количество вакансий, дату обновления и список источников.
4. **Округление консистентное.** Везде до сотен (100, 200, 500, не «81 250»). Применяется на финальном шаге, не в промежуточных вычислениях.
5. **Дубли — главный враг чистоты.** Считаем как одну запись, не теряем источниковую информацию.

## Источники (по приоритету релевантности для редакторов/копирайтеров)

1. **Habr Career** — открытые страницы вакансий + публичный salary report. Высокая релевантность.
2. **Telegram-каналы** — публичные каналы с вакансиями, читаем через MTProto API, текст постов прогоняем через LLM для извлечения структуры (должность, вилка, город, навыки, тип занятости).
3. **SuperJob** — официальный API, средняя релевантность, традиционные работодатели.
4. **Trudvsem.ru** — открытый госpub API, низкая релевантность для нашей ниши, оставляем для широты охвата.

Парсинг hh.ru — не используется (серый юридический статус).

## Фильтрация спама и фейков

Применяется ко всем источникам перед записью в наш стор.

### Базовые правила

- **Без зарплаты** → отбрасываем. `agreement=true` или `from=to=0` — пропускаем.
- **Кадровые агентства** → отбрасываем по списку маркеров в названии работодателя (`кадров`, `рекрутинг`, `hh-агент`, `подбор персонала`, `хедхант`, …).
- **Слишком короткое описание** → отбрасываем, если суммарно `work + candidat` короче 100 символов. Это обычно автогенерированный мусор.

### Выбросы по зарплате

- Считаем медиану и стандартное отклонение по профессии × региону.
- Отбрасываем вакансии с зарплатой больше **3 SD** от медианы. Это режет «600к в первый месяц для копирайтера» — пирамиды, инфобиз, манипуляции.
- Симметрично: вакансии меньше 0.3× медианы — тоже подозрительны (стажировки за еду, мошенничество).

### Подозрительные паттерны

Отбрасываем вакансии, в описании которых встречаются маркеры пирамид и MLM:

`сетевой маркетинг`, `сетевой бизнес`, `пассивный доход`, `инвестиции в крипту`, `bitcoin`, `создай свой бизнес», «свободный график без вложений», «доход от 200 тысяч в первый месяц», вебинары с продажей курсов на ту же тему.

Список маркеров живёт в `src/filters/spam-keywords.ts` и пополняется по мере находок.

### Дубли работодателя

Если один работодатель публикует > 5 одинаковых вакансий с разницей в копейку — считаем за одну. Это часто массовая публикация одного шаблона.

## Дедупликация

### Внутри источника
- БД (или JSON-индекс) имеет `UNIQUE(source, source_id)`.
- Дубль физически невозможен записать.

### Между источниками
- Fuzzy-match по ключу `(work_employer_normalized, profession_normalized, city, salary_range_with_tolerance)`.
- Нормализация работодателя: убираем ООО, ИП, кавычки, приводим к нижнему регистру.
- Толеранс по зарплате: вилки совпадают, если пересечение ≥ 80%.
- Найденные дубли **помечаются**, а не удаляются — для отладки и прозрачности.
- В подсчёте медианы дубль учитывается **один раз**.

## Извлечение навыков

### Сегодня
- Keyword-matching по словарю в `src/lib/superjob-api.ts` (`SKILLS_BY_PROFESSION`).
- Из текста `profession + work + candidat` ищем вхождения.

### Что улучшим
- Дополнить keyword-matching LLM-извлечением для неточных формулировок. Например, «понимание SQL на базовом уровне» → SQL.
- Кэшировать результат LLM-разбора по `vacancy_id`, чтобы не платить за один и тот же текст дважды.
- Раз в месяц пересматривать список навыков и их синонимов — добавлять новые («работа с Claude», «MCP», «AI Agents» сейчас, например).

### Сортировка и отсев
- Сортируем по `count` — частоте упоминаний в вакансиях. Самые популярные сверху.
- **Отсекаем** навыки, упомянутые в менее чем **3% вакансий** по профессии. Это шум.
- Минимум **10 упоминаний абсолютно**, иначе не показываем — слишком мало для медианы.

## Расчёт salary_impact для навыка

### Метод

Для каждого навыка:

```
medianWith    = медиана зарплат В вакансиях, где навык упомянут
medianWithout = медиана зарплат В вакансиях, где навык НЕ упомянут
salary_impact = medianWith - medianWithout
```

### Что значит для трёх звёзд

```
basic     (1 звезда): salary_impact × 0.30
confident (2 звезды): salary_impact × 0.60
expert    (3 звезды): salary_impact × 1.00
```

Эти коэффициенты — это не точная наука, а удобное приближение: базовый уровень даёт треть прибавки, уверенный — половину, экспертный — полную. Если данные покажут, что распределение другое (например, в реальности базовый уровень даёт 50%) — пересмотрим.

### Округление

- На вход — рубли как есть.
- Финальный `salary_impact` → округление до **100 ₽**.
- Если `salary_impact < 1000 ₽` → не показываем навык вообще: разница незначимая.

## Описания уровней

Сегодня описания «Базовый / Уверенный / Продвинутый» зашиты в `updateData.ts`.

Проблема: то, что 2 года назад считалось продвинутым (например, «настроить таргет в VK»), сейчас базовое требование. Описания устаревают.

### План
- Раз в **3 месяца** прогоняем все описания через LLM с промптом: «Вот навык, вот 20 случайных вакансий, где он упомянут, — какие реальные требования сегодня считаются базовыми, какие продвинутыми? Перепиши описания».
- LLM-сгенерированные описания записываются в `src/data/skill-descriptions.json`, переопределяя дефолтные.

## Расписание сбора

| Частота | Что делаем |
|---|---|
| Ежедневно (cron 03:00 UTC) | Собираем новые вакансии со всех источников, фильтруем, дедуплицируем, мержим в наш стор |
| Раз в неделю | Пересчитываем медианы и `salary_impact` по всем профессиям и регионам |
| Раз в 3 месяца | Прогоняем описания уровней через LLM, обновляем `skill-descriptions.json` |

## Низкое количество данных

Если по сочетанию **профессия × регион**:

- < **30 вакансий** → показываем «недостаточно данных по этому региону, скоро обновим». Не выводим случайную медиану.
- < **100 вакансий** → выводим медиану с пометкой «выборка небольшая, точность ниже».
- ≥ 100 → выводим без пометок.

Для **навыков**:

- < 10 упоминаний → не показываем.
- 10–30 → показываем с пометкой «оценка предварительная».
- ≥ 30 → показываем без пометок.

## Расширение географии

Города живут в `src/lib/cities.ts`:

```ts
export const CITIES = {
  moscow: { name: 'Москва', sj_id: 4, hh_id: 1, ... },
  spb:    { name: 'Санкт-Петербург', sj_id: 14, hh_id: 2, ... },
  ...
}
```

Каждый источник нужен свой ID, потому что у каждой площадки своя нумерация. Чтобы добавить город — добавляем запись в этот файл, и сбор автоматически расширяется.

## Что не делаем

- Не показываем средние арифметические. Только медианы.
- Не учитываем зарплаты «по договорённости» (всегда отбрасываем).
- Не сохраняем персональные данные пользователей (даже если когда-то будет форма самоотчёта — анонимно).
- Не делаем «обещания точности до рубля» в пользовательских формулировках — везде «оценка», «ориентир».
